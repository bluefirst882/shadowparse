> `NoSuchMethodError`。跑 `verify` 时请把 `JAVA_HOME` 指向标准 JDK 21（如 Temurin）。

## 2026-09-27 JSON Schema 结构约束与模型降级链实测

```powershell
.\mvnw.cmd -f backend\pom.xml verify
docker compose build backend
$env:LLM_MODEL='deepseek-v4-flash-nonexistent'   # 仅本次 shell 生效，不改 .env
docker compose up -d --wait backend
docker compose exec -T backend printenv LLM_MODEL LLM_FALLBACK_MODEL
```

- **先实测供应商能力，再选实现方式**（直接对 DeepSeek 官方 API 发探针请求，结果记入 README）：
  - `response_format={"type":"json_schema","json_schema":{...,"strict":true}}` → HTTP `400`，`This response_format type is unavailable now`；
  - 强制 function calling（`tools` + `tool_choice={"type":"function",...}`）→ HTTP `400`，`Thinking mode does not support this tool_choice`；
  - `response_format={"type":"json_object"}` → HTTP `200`；
  - `GET /v1/models` 返回 `deepseek-flash`、`deepseek-v4-pro`，即 `.env` 里的 `deepseek-v4-flash` 被解析为 `deepseek-flash`；
  - 传入不存在的模型名 → HTTP `400`（正好用作「模拟主模型故障」的探针）。
  结论：只能走「`json_object` + 提示词内 schema 原文 + 本地 schema 校验」，不能依赖供应商侧结构化输出。
- 本地校验：`LlmJsonSchema` 是摘要 / 跨块合并 / 翻译三份 schema 的唯一来源，同一份原文既进提示词也进本地校验；
  违规按 JSON 路径逐条报出（`$.chapters[0].quote 缺少必填字段`、`$.chapters[0].title 期望 string，实际为 number`），
  超过 10 条时截断并追加「其余违规已省略」，避免错误信息无限膨胀。
- 后端：`Tests run: 87, Failures: 0, Errors: 0, Skipped: 3`（3 项 MySQL 集成测试未配置 `MYSQL_TEST_URL` 时跳过），Spotless 通过。
  新增 `LlmJsonSchemaTest`（9 项：合法输出、顶层/嵌套/数组元素缺字段、类型错误带路径与实际类型、`1000.0` 视为合法整数、
  根类型不匹配、违规截断、TRANSLATE schema）与 `LlmClientFallbackTest`（6 项：主模型 400 降级成功、
  输出缺 `quote` 触发 `schema_violation` 降级、空内容 `empty_content`、两端都失败抛异常、未配置备用模型不回退、备用模型同名不回退）。
- **降级链真实生效**：把容器主模型覆盖为不存在的 `deepseek-v4-flash-nonexistent`（备用模型仍为 `deepseek-v4-pro`），
  对已有任务 `f1094e67-33da-4038-9935-25557bc50288` 触发 `retry`，约 140 秒后达到 `COMPLETED/COMPLETED`，
  `keyPoints=5 chapters=5`。主模型全程 400，任务却依然完成，说明备用模型确实接住了请求。
  日志证据（后端 WARN）：

  ```text
  模型 deepseek-v4-flash-nonexistent 调用失败（http_400）：内容服务返回 HTTP 400：
  {"error":{"message":"The supported API model names are deepseek-flash, deepseek-v4-pro,
  but you passed deepseek-v4-flash-nonexistent. ...
  ；降级到 deepseek-v4-pro
  ```

  指标证据：`workbench_llm_fallbacks_total{operation="summarize",reason="http_400"} 2.0`
  （两次调用各降级一次），同时 `workbench_llm_requests_total{operation="summarize",outcome="failure"} 2.0`
  如实记录主模型失败，降级没有把失败抹平。
- **恢复真实主模型后无误报**：移除 shell 覆盖并用 `docker compose up -d --wait backend` 重建容器，
  容器内确认 `LLM_MODEL=deepseek-v4-flash`、`LLM_FALLBACK_MODEL=deepseek-v4-pro`；
  再次对同一任务 `retry`，24 秒达到 `COMPLETED/COMPLETED`（`keyPoints=7 chapters=7`，引文均通过闸门），
  此时 `/actuator/prometheus` 中**没有** `workbench_llm_fallbacks_total` 时间序列（计数器未注册即为 0），
  说明降级只在主模型真的失败时触发，正常路径不会产生降级噪音。
