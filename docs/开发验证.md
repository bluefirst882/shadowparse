## 2026-09-27 JSON Schema 结构约束与模型降级链实测

```powershell

```

- **先实测供应商能力，再选实现方式**（直接对 DeepSeek 官方 API 发探针请求，结果记入 README）：
  - `response_format={"type":"json_schema","json_schema":{...,"strict":true}}` → HTTP `400`，`This response_format type is unavailable now`；
  - 强制 function calling（`tools` + `tool_choice={"type":"function",...}`）→ HTTP `400`，`Thinking mode does not support this tool_choice`；
  - `response_format={"type":"json_object"}` → HTTP `200`；
  - `GET /v1/models` 返回 `deepseek-flash`、`deepseek-v4-pro`，即 `.env` 里的 `deepseek-v4-flash` 被解析为 `deepseek-flash`；

- 本地校验：`LlmJsonSchema` 是摘要 / 跨块合并 / 翻译三份 schema 的唯一来源，同一份原文既进提示词也进本地校验；

  超过 10 条时截断并追加「其余违规已省略」，避免错误信息无限膨胀。

## 2026-09-27 任务队列外置到 RabbitMQ 实测（P2-1）

```powershell
docker compose up -d --wait rabbitmq
docker compose build backend; docker compose up -d --wait backend
.\mvnw.cmd -f backend\pom.xml verify
# 造一个 20 秒小样本，走一次完整上传链路
ffmpeg -i "<源视频>" -t 20 -c copy backend\target\p21-sample.mp4
# 停机后直投重复消息（消息落在 broker 上，模拟「重启前入队」）
docker compose stop backend
# 库里把该任务改回 QUEUED/IMPORT 后，用管理 API 向 workbench.tasks 直投 3 条相同消息
Invoke-RestMethod -Uri "http://localhost:15672/api/exchanges/%2F/amq.default/publish" -Method Post `
  -ContentType 'application/json' -Body '{"properties":{},"routing_key":"workbench.tasks","payload":"<taskId>","payload_encoding":"string"}'
docker compose start backend
docker compose logs backend | Select-String "跳过重复投递"
```

- 拓扑：`TaskQueueConfig` 声明三个**持久化**队列 —— 主队列 `workbench.tasks`（DLX 指向 `workbench.tasks.dlx`）、
  重试队列 `workbench.tasks.retry`（DLX routing key 回 `tasks`）、死信队列 `workbench.tasks.dead`；
  消息以 `PERSISTENT` 投递模式发送，broker 重启也不丢。
- 投递路径：`TaskService` 只依赖 `TaskQueue` 接口，`RabbitTaskQueue` 是唯一实现；投递用默认交换机 + routing key = 队列名，
  发送后通过 `CorrelationData.getFuture()`（配 `publisher-confirm-type: correlated`）等 broker 确认，
  确认失败只计 `workbench.queue.publish_failures` 并记 ERROR 日志，不自动重投。
- 消费路径：`TaskQueueConsumer` 用 `@RabbitListener(autoStartup="false")`，由 `TaskRecovery` 在
  `recoverAfterRestart()` **之后**才 `start()`；`prefetch=1`、`concurrency=1`、手动 ack，
  异常时 `basicNack(requeue=true)` 退回队列。
- 幂等实测（计划验收第 1 条「重复投递只被消费一次」）：把一条已完成任务改回 `QUEUED/IMPORT`，
  在 backend **停机期间**直投 3 条内容相同的消息，重启后日志出现 **3 次**
  「任务已被领取或已结束，跳过重复投递」；加上启动恢复自己重投的 1 条，共 4 条消息，该任务最终 `COMPLETED`，
  只被真正处理 1 次。判定点是 `TaskRepository.claimForProcessing` 的条件更新
  （`update ... where id=? and status='QUEUED' and cancelled=false`），重复投递第二次必然领不到。
- 重启不丢任务实测（验收第 2 条）：上述 3 条消息是在进程停止期间投递的，broker 持久化保存，
  后端重启后被正常消费——即「已入队的任务不会因为进程重启而丢失」。
- 正常链路实测：20 秒样本（0.74 MB）上传后状态依次为 `QUEUED` → `TRANSCRIPTION(45%)` → `SUMMARY(85%)` → `COMPLETED`，约 27 秒。
- consumer_timeout：RabbitMQ 默认 30 分钟，短于本项目的 `WORKBENCH_PROCESS_TIMEOUT_MINUTES=180`，
  长视频转到一半会被 broker 强制关 channel；compose 里通过
  `RABBITMQ_SERVER_ADDITIONAL_ERL_ARGS='-rabbit consumer_timeout 86400000'` 放宽到 24 小时，
  容器内 `rabbitmqctl eval 'application:get_env(rabbit, consumer_timeout).'` 返回 `{ok,86400000}`。
- 指标实测：`workbench_queue_depth 0.0`（`RabbitTaskQueue` 用 `AmqpAdmin.getQueueProperties` 读 broker 真实积压量，
  读不到返回 `-1` 而不是 `0`）、`workbench_queue_wait_seconds_count 1`（正常上传路径记到 1 次等待时长；
  管理 API 直投的消息没有 `timestamp` 属性，故不计入等待）、`workbench_queue_publish_failures_total` 不存在（本次无投递失败）。
- 测试：新增 `RabbitTaskQueueTest`（5 项：持久化投递、broker 不可达抛 `UnavailableException`、确认被拒时计数、
  队列深度 3、读不到时 -1）与 `TaskQueueConsumerTest`（4 项：正常 ack、异常 nack + requeue、等待时长计时、
  取不到容器时 `start` 不抛出）；`TaskServiceTest` 改为注入 `TaskQueue` mock，新增
  「重试投递不再重置任务」「投递失败返回 503」「任务已删除时丢弃投递」「已被领取时跳过重复投递」
  「队列不可用时保存任务并提示稍后重试」5 项，删除已不存在的「队列满」与「重复重试冲突」2 项。

  `MYSQL_TEST_URL` 时跳过），Spotless 通过。

- 失败分流：`TransientFailure` 只在「等一会儿重来可能就好」的位置抛出——`runWhisper` 的连接失败 / 读超时 /
  5xx 记为 `whisper_unavailable`，数据库异常（`DataAccessException`）在消费者侧归一为 `database_unavailable`；
  Whisper 返回 4xx、FFmpeg 退出码非 0、媒体损坏等**不属瞬时故障**，不占用重试额度，直接判 `FAILED`。
- 退避时间由 broker 的消息 TTL 承载（`publishRetry` 设 `expiration` + `x-attempt` 头），不在进程里 sleep：
  第 n 次失败后等 `初始延迟 × 倍率^(n-1)`，默认 5s → 10s → 20s，单个延迟上限 6 小时（配置放大重试次数时兜底）。
- 重试消息到期后由重试队列自身的 DLX 按 `tasks` 路由键回到主队列，作为一次新的投递被消费；
  任务在瞬时故障后会被放回 `QUEUED`，因此这次投递能重新领取到它。若上次尝试被基础设施故障打断、
  任务仍停在 `PROCESSING`，重试投递会先 `releaseProcessing` 把它放回 `QUEUED` 再领取（第 1 次投递不做这件事，
  避免把别的执行者正在处理的任务抢过来）。

```powershell
docker exec toni-2-mysql-1 mysql -uroot -padmin video_workbench -N -e `

# 两个实例各自的领取读数
docker exec toni-2-backend-1 sh -c "curl -s localhost:8080/actuator/prometheus" | Select-String task_claims
docker exec toni-backend-b   sh -c "curl -s localhost:8080/actuator/prometheus" | Select-String task_claims

# 重复投递注入：把已 COMPLETED 的任务 id 再直投一次
$b64 = [Convert]::ToBase64String([Text.Encoding]::ASCII.GetBytes('workbench:workbench-local'))
$body = @{properties=@{delivery_mode=2}; routing_key='workbench.tasks'; payload='<taskId>'; payload_encoding='string'} | ConvertTo-Json -Compress
Invoke-RestMethod -Uri 'http://127.0.0.1:15672/api/exchanges/%2F/amq.default/publish' -Method Post `
  -Headers @{Authorization="Basic $b64"} -ContentType 'application/json' -Body $body

# 崩溃接管：让 B 领到一个长任务，然后 SIGKILL（不走 @PreDestroy，不交还租约）
docker kill toni-backend-b        # 事后 docker ps -a 显示 Exited (137)
docker logs toni-2-backend-1 --since 5m | Select-String "租约已过期"

# 收尾
docker rm -f toni-backend-b
```

- 方案要点：`claimForProcessing` 依旧是幂等唯一裁决点（`where id=? and status='QUEUED' and cancelled=false`），
  只是顺手写入 `locked_by` + `lease_expires_at`（迁移 V5 加两列 + `idx_tasks_lease`）。
  心跳只续内存 `held` 集合里的任务（**不续被放弃的行**，否则它会永不过期）；
  巡检只收 `status='PROCESSING' and lease_expires_at < now` 的行，迁移前遗留的 `lease_expires_at is null`
  行按已过期处理，升级期间被中断的任务不会卡住。
- 旧方案的两个漏洞：启动恢复把**所有** `PROCESSING` 改回 `QUEUED`，第二个实例一启动就打断第一个实例正在跑的任务；
  且没有字段能区分「别人在跑」与「持有者已死」。
- 三种恢复路径各归其位：优雅停机 `@PreDestroy` 立即交还；`SIGKILL` 靠租约过期 + 巡检回收；
  重试投递（`attempt>1`）只在「持有者是自己」或「租约已过期」时就地放回，否则跳过。
- 两实例实测：6 个任务，在 A 正处理第 1 个任务时启动 B——该任务 `locked_by` 全程保持 A 并正常 `COMPLETED`；
  两实例持有的任务从不重叠，6 个全部 `COMPLETED/COMPLETED`、`locked_by` 与 `lease_expires_at` 全部回到 `NULL`，
  全程约 2 分钟。指标 A `claimed=4 / skipped=5`、B `claimed=3`，B 启动日志
  「启动恢复发现 5 条排队中的任务，重新投递」正好对应 A 侧的 5 次 `skipped`。
- 重复投递注入：3 个已完成任务各直投一次 → A 记 2 次、B 记 1 次「跳过重复投递」，
  `{result="skipped"}` 由 5/0 升到 7/1，三条任务的 `transcript_segments`（各 8 行）、`llm_calls`（各 1 行）**无新增**。
- 崩溃接管：B 领到 `f9a453fb-…`（`lease_expires_at` `16:05:18.947` UTC），在 `16:05:16.717` 执行
  `docker kill`（比租约到期早 2.2 秒，`docker ps -a` 显示 `Exited (137)`）；A 于 `16:05:59.277` 打出
  「任务租约已过期，收回并重新投递：… 上一次持有者已失联」并重新领取。该任务全程只有这一条回收记录。
  时间关系符合预期：租约到期 + 巡检间隔 30 s 内被扫到。

## 2026-09-29 Whisper 容器化实测（P3-1）

构建与启动（首次构建约十分钟，依赖 CPU 版 torch 等约 1GB 下载）：

```powershell
docker compose build whisper
docker compose up -d whisper
docker compose ps whisper                       # toni-2-whisper-1  Up (healthy)
curl.exe -s http://127.0.0.1:8090/health        # {"status": "ok", "device": "cpu", "model": "turbo"}
docker compose logs whisper --tail 2            # 先 "model ready" 后 "listening"，证明端口是在模型加载完后才开的
docker inspect toni-2-whisper-1 --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{end}}'
# E:\program\project\toni-2\models\whisper -> /models
```

直接调用转写（40 秒 16kHz 单声道样本，`elapsed=32.5s`，返回 7 个片段）：

```powershell
& 'D:/program/anaconda/Library/bin/ffmpeg.exe' -y -loglevel error -ss 0 -t 40 `
  -i 'storage\00a77f23-a070-4fb7-919a-8265132515d4.wav' -ar 16000 -ac 1 -c:a pcm_s16le "$env:TEMP\p31-sample.wav"
$token = (Get-Content .env | Where-Object { $_ -match '^WHISPER_SERVICE_TOKEN=' }).Substring(22)
$arg = "@$env:TEMP\p31-sample.wav"   # 必须以 @ 开头；写成 -@ 会被 curl 当字面量，Whisper 侧报 ffmpeg 无法解码
curl.exe -s -X POST -H "X-Whisper-Token: $token" -H "X-Whisper-Model: turbo" `
  --data-binary $arg http://127.0.0.1:8090/transcribe
```

串行保护与自愈：

```powershell
# 同一段音频并发两次：分别 32.8s / 64.8s，第二个完整等锁 → /transcribe 是串行的
# 崩溃自愈：从祖先 PID 命名空间 SIGKILL 主进程（注意不是 docker kill，见下方说明）
$vmPid = (docker inspect toni-2-whisper-1 --format '{{.State.Pid}}')
docker run --rm --pid=host --entrypoint sh toni-2-whisper -c "kill -9 $vmPid"
docker inspect toni-2-whisper-1 --format 'RestartCount={{.RestartCount}}'   # 1；+35s 恢复 healthy
```

端到端：`docker compose up -d backend` 让后端拿到 `WHISPER_SERVICE_URL=http://whisper:8090`，
上传 134.167 秒视频后 `+130s COMPLETED/COMPLETED`，持久化 105 个片段、9 个章节。

- 踩坑记录：`docker kill toni-2-whisper-1` 属于**显式停止**，`restart: unless-stopped` 不会重启它
  （实测停在 `Exited (137)`、`RestartCount=0`），恢复要用 `docker compose start whisper`；
  在容器内 `kill -9 1` 也无效（PID 1 只接受来自祖先命名空间的信号）。要模拟「进程自己死掉」，
  必须从宿主/祖先命名空间发信号，本次用 `--pid=host` 的一次性容器执行 `kill -9`。
- `mvnw verify`：`Tests run: 135, Failures: 0, Errors: 0, Skipped: 4`，Spotless 通过（本次未改 Java 代码）。

## 2026-09-29 k6 压测实测（P3-2）

压测脚本在 `ops/k6/`，用官方镜像跑在 compose 网络内，直接打容器内的 8080（宿主 8081 只是映射端口）：

```powershell
# 第一轮只读阶梯：20 → 40 → 80 → 120 次/秒，每档 30s
docker run --rm --network toni-2_default -v "$PWD/ops/k6:/scripts" -w /scripts `
  -e BASE_URL=http://backend:8080 -e READ_TARGETS=40,80,120,120 -e READ_STAGE_DURATION=30s `
  -e RESULT_NAME=read-1 grafana/k6 run query.js

# 第二轮只读阶梯：100 → 200 → 300 → 400 次/秒
docker run --rm --network toni-2_default -v "$PWD/ops/k6:/scripts" -w /scripts `
  -e BASE_URL=http://backend:8080 -e READ_TARGETS=100,200,300,400 -e READ_STAGE_DURATION=30s `
  -e RESULT_NAME=read-2 grafana/k6 run query.js

# 上传：恒定 2 次/秒（fixture 为先在本机切出来的 48,701 字节 4 秒片段）
docker run --rm --network toni-2_default -v "$PWD/ops/k6:/scripts" -w /scripts `
  -e BASE_URL=http://backend:8080 -e UPLOAD_RATE=2 -e UPLOAD_DURATION=20s `
  -e RESULT_NAME=upload-1 grafana/k6 run upload.js
```

边压边采样队列深度与该批次任务状态分布（写 `ops/k6/results/queue.csv`）：

```powershell
pwsh -File ops/k6/sample-queue.ps1 -Samples 42 -IntervalSeconds 5 -FileNamePattern 'sample-4s%'
```

服务端侧分位数直接从 Prometheus 取（**表达式里不要带双引号**，见踩坑）：

```powershell
curl.exe -sG 'http://127.0.0.1:9090/api/v1/query' `
  --data-urlencode 'query=histogram_quantile(0.95, sum by (le, uri) (rate(http_server_requests_seconds_bucket[10m])))'
```

实测：只读两轮共 43000+ 请求、`http_req_failed` 与 `dropped_iterations` 均为 0，400 次/秒到达率下
P95 列表 2.14ms / 详情 1.93ms / 明细 3.11ms；稳态 200 次/秒 × 40s（8001 请求）服务端侧 P95 为
列表 2.05ms / 详情 1.83ms / 明细 3.02ms、P99 6.78ms；上传两轮共 101 个任务、P95 约 15ms、零失败。
资源：backend 37–48% CPU / 557MiB、mysql 14–17% / 199MiB、Hikari `pending` 全程 0。
**读接口没压出拐点**；瓶颈在处理侧——队列深度涨到 97、排空速率约 2 个/分钟。

- 踩坑记录（按踩到的顺序）：
  - **容器内的后端监听 8080，不是 8081**。先用 `BASE_URL=http://backend:8081` 时 k6 在 `setup()` 里
    登录就拿到 HTTP 0（`dial tcp 172.18.0.3:8081: connect: connection refused`）——8081 只是宿主映射端口。
  - **Timer 默认不导出 `_bucket`**。Panel 一开始是 No data：`/actuator/prometheus` 只有
    `http_server_requests_seconds_count/_sum/_max`，`histogram_quantile` 自然返回空。已在
    `application.yml` 打开 `management.metrics.distribution.percentiles-histogram.http.server.requests`，
    重建后端后该指标有 138 条 `_bucket`（Prometheus 414 条 series），面板出曲线。
  - **PowerShell 5.1 会吞掉传给原生 curl 的双引号**：Prometheus 查询里写 `uri!~"/actuator.*"` 会报
    `parse error: unexpected character inside braces: '/'`；改成不含引号的表达式即可。
  - **不要给采样脚本设 `$ErrorActionPreference='Stop'`**：`docker compose exec -T mysql` 会往 stderr 写
    `Using a password on the command line interface can be insecure`，PowerShell 7 把它当
    NativeCommandError 直接终止脚本（日志里 exit code 1）。去掉该设置后正常。
  - **`Invoke-WebRequest.Content` 在 PS7 下可能是 `byte[]`**，正则会匹配不到；要判断
    `$response.Content -is [byte[]]` 后用 `[System.Text.Encoding]::UTF8.GetString` 解码。
  - `docker compose build backend | Select-Object -Last N` 会缓冲到命令结束才输出，日志文件长时间为 0 字节
    属正常现象，用 `docker images toni-2-backend --format {{.CreatedSince}}` 判断进度。
- 局限：单机同机压测、上传只压接收路径、未做 soak 与读写混合、读接口未压出拐点故不给最大 QPS，
  详见 [docs/端到端验收记录.md](端到端验收记录.md) 的「2026-09-29 压测与容量说明（P3-2）」。
