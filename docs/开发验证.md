## 2026-09-27 JSON Schema 结构约束与模型降级链实测

```powershell

```

- **先实测供应商能力，再选实现方式**（直接对 DeepSeek 官方 API 发探针请求，结果记入 README）：
  - `response_format={"type":"json_schema","json_schema":{...,"strict":true}}` → HTTP `400`，`This response_format type is unavailable now`；
  - 强制 function calling（`tools` + `tool_choice={"type":"function",...}`）→ HTTP `400`，`Thinking mode does not support this tool_choice`；
  - `response_format={"type":"json_object"}` → HTTP `200`；
  - `GET /v1/models` 返回 `deepseek-flash`、`deepseek-v4-pro`，即 `.env` 里的 `deepseek-v4-flash` 被解析为 `deepseek-flash`；

- 本地校验：`LlmJsonSchema` 是摘要 / 跨块合并 / 翻译三份 schema 的唯一来源，同一份原文既进提示词也进本地校验；

  超过 10 条时截断并追加「其余违规已省略」，避免错误信息无限膨胀。

## 2026-09-27 任务队列外置到 RabbitMQ 实测（P2-1）

```powershell
docker compose up -d --wait rabbitmq
docker compose build backend; docker compose up -d --wait backend
.\mvnw.cmd -f backend\pom.xml verify
# 造一个 20 秒小样本，走一次完整上传链路
ffmpeg -i "<源视频>" -t 20 -c copy backend\target\p21-sample.mp4
# 停机后直投重复消息（消息落在 broker 上，模拟「重启前入队」）
docker compose stop backend
# 库里把该任务改回 QUEUED/IMPORT 后，用管理 API 向 workbench.tasks 直投 3 条相同消息
Invoke-RestMethod -Uri "http://localhost:15672/api/exchanges/%2F/amq.default/publish" -Method Post `
  -ContentType 'application/json' -Body '{"properties":{},"routing_key":"workbench.tasks","payload":"<taskId>","payload_encoding":"string"}'
docker compose start backend
docker compose logs backend | Select-String "跳过重复投递"
```

- 拓扑：`TaskQueueConfig` 声明三个**持久化**队列 —— 主队列 `workbench.tasks`（DLX 指向 `workbench.tasks.dlx`）、
  重试队列 `workbench.tasks.retry`（DLX routing key 回 `tasks`）、死信队列 `workbench.tasks.dead`；
  消息以 `PERSISTENT` 投递模式发送，broker 重启也不丢。
- 投递路径：`TaskService` 只依赖 `TaskQueue` 接口，`RabbitTaskQueue` 是唯一实现；投递用默认交换机 + routing key = 队列名，
  发送后通过 `CorrelationData.getFuture()`（配 `publisher-confirm-type: correlated`）等 broker 确认，
  确认失败只计 `workbench.queue.publish_failures` 并记 ERROR 日志，不自动重投。
- 消费路径：`TaskQueueConsumer` 用 `@RabbitListener(autoStartup="false")`，由 `TaskRecovery` 在
  `recoverAfterRestart()` **之后**才 `start()`；`prefetch=1`、`concurrency=1`、手动 ack，
  异常时 `basicNack(requeue=true)` 退回队列。
- 幂等实测（计划验收第 1 条「重复投递只被消费一次」）：把一条已完成任务改回 `QUEUED/IMPORT`，
  在 backend **停机期间**直投 3 条内容相同的消息，重启后日志出现 **3 次**
  「任务已被领取或已结束，跳过重复投递」；加上启动恢复自己重投的 1 条，共 4 条消息，该任务最终 `COMPLETED`，
  只被真正处理 1 次。判定点是 `TaskRepository.claimForProcessing` 的条件更新
  （`update ... where id=? and status='QUEUED' and cancelled=false`），重复投递第二次必然领不到。
- 重启不丢任务实测（验收第 2 条）：上述 3 条消息是在进程停止期间投递的，broker 持久化保存，
  后端重启后被正常消费——即「已入队的任务不会因为进程重启而丢失」。
- 正常链路实测：20 秒样本（0.74 MB）上传后状态依次为 `QUEUED` → `TRANSCRIPTION(45%)` → `SUMMARY(85%)` → `COMPLETED`，约 27 秒。
- consumer_timeout：RabbitMQ 默认 30 分钟，短于本项目的 `WORKBENCH_PROCESS_TIMEOUT_MINUTES=180`，
  长视频转到一半会被 broker 强制关 channel；compose 里通过
  `RABBITMQ_SERVER_ADDITIONAL_ERL_ARGS='-rabbit consumer_timeout 86400000'` 放宽到 24 小时，
  容器内 `rabbitmqctl eval 'application:get_env(rabbit, consumer_timeout).'` 返回 `{ok,86400000}`。
- 指标实测：`workbench_queue_depth 0.0`（`RabbitTaskQueue` 用 `AmqpAdmin.getQueueProperties` 读 broker 真实积压量，
  读不到返回 `-1` 而不是 `0`）、`workbench_queue_wait_seconds_count 1`（正常上传路径记到 1 次等待时长；
  管理 API 直投的消息没有 `timestamp` 属性，故不计入等待）、`workbench_queue_publish_failures_total` 不存在（本次无投递失败）。

## 2026-09-27 退避重试与死信实测（P2-2）

```powershell
# 故障注入：把后端的 Whisper 地址指向没人监听的端口，制造「Whisper 不可达」瞬时故障
```

- 失败分流：`TransientFailure` 只在「等一会儿重来可能就好」的位置抛出——`runWhisper` 的连接失败 / 读超时 /
  5xx 记为 `whisper_unavailable`，数据库异常（`DataAccessException`）在消费者侧归一为 `database_unavailable`；
  Whisper 返回 4xx、FFmpeg 退出码非 0、媒体损坏等**不属瞬时故障**，不占用重试额度，直接判 `FAILED`。
- 退避时间由 broker 的消息 TTL 承载（`publishRetry` 设 `expiration` + `x-attempt` 头），不在进程里 sleep：
  第 n 次失败后等 `初始延迟 × 倍率^(n-1)`，默认 5s → 10s → 20s，单个延迟上限 6 小时（配置放大重试次数时兜底）。
- 重试消息到期后由重试队列自身的 DLX 按 `tasks` 路由键回到主队列，作为一次新的投递被消费；
  任务在瞬时故障后会被放回 `QUEUED`，因此这次投递能重新领取到它。若上次尝试被基础设施故障打断、
  任务仍停在 `PROCESSING`，重试投递会先 `releaseProcessing` 把它放回 `QUEUED` 再领取（第 1 次投递不做这件事，
  避免把别的执行者正在处理的任务抢过来）。
