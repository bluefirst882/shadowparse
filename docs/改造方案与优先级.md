# 改造方案与落地优先级

对标 [DOVideo-AI](https://github.com/Xiaoc7r/DOVideo-AI) 后确定的三 个改造方向，按「护栏 → 价值 → 架构」排序。
每个方向给出：现状锚点（代码位置）、方案、数据模型、验收标准、风险与回滚。

## 优先级总览

| 优先级 | 方向                        | 理由                                                                             | 预估工作量             |
| ------ | --------------------------- | -------------------------------------------------------------------------------- | ---------------------- |
| P0     | LLM 成本护栏（限流 + 预算） | 改动最小、堵住唯一的成本敞口；基建（Resilience4j、llm_calls 表）已就位           | 1–2 天                 |
| P1     | 视觉分支（关键帧 + OCR）    | 对章节质量提升最大；只加分支不动既有校验链路                                     | 3–5 天                 |
| P2     | 向量召回                    | **有前置条件**：当前产品没有「查询」动作，向量检索没有服务对象；必须先加追问交互 | P2a 1–2 天，P2b 4–6 天 |

排序原则：P0 是花钱的保险丝，先装；P1 是用户可感知的价值；P2 是架构升级，但不解决「谁在检索」之前不做。

## 已确认决策（2026-10-07 方案评审）

| # | 决策点 | 结论 | 影响 |
| --- | --- | --- | --- |
| 1 | 改造目的 | 真实可用与叙事兼顾，每个方向都要有可量化的验收数据 | 各方向验收标准必须落到具体数字 |
| 2 | 部署预期 | 先自用，结构上预留少数人共用 | P0 预算按「用户记账、全局兜底」设计；用户配额默认关闭 |
| 3 | 超预算行为 | **降级续跑**，不 FAILED：切到便宜的 fallback 模型继续，复用现有模型降级链 | 修改原「任务 FAILED」设计，见 P0 方案 |
| 4 | OCR 引擎 | Tesseract 5.4（`chi_sim` + `eng`），`OcrEngine` 接口抽象保留换 PaddleOCR 的路径 | 验收须实测中文命中率基准 |
| 5 | P1 交付边界 | 前后端一起做：帧缩略图条 + 点击跳转播放 + OCR 文本展示 | 验收含可交互效果，多 1–2 天 |
| 6 | 本轮范围 | **P0 + P1 + P2a**，P2b（向量召回）暂缓至有真实长视频追问需求 | 总周期约 7–9 天 |

## P0：LLM 成本护栏

### 现状

- `LlmClient.summarize`（`LlmClient.java:88-102`）按 `maxInputChars`（默认 60000，`application.yml:108`）分块，**每块一次 LLM 调用，循环无总量上限**。一个 10 小时视频 ≈ 60+ 次调用，没有任何闸门。
- 已有：`bulkhead.llm`（并发 4，`application.yml:68`）+ 熔断器——它们管「同时多少个」，不管「一共多少个」「多快」。
- `llm_calls` 表（V4 迁移）+ `LlmCostService` 已按 prompt 版本记录 token 与金额，**记账有了，限流没有**。
- 消费并发固定为 1（`TaskQueueConsumer.java:24`），所以限流对象是「单个任务内部的多块调用」，不是多任务并发。

### 方案

1. **速率层：Resilience4j RateLimiter（令牌桶）包住 `LlmClient.requestJson`**
   - 按每分钟请求数限流：`workbench.llm.rate-limit-rpm`（默认 30）。
   - 熔断/隔板是「下游坏了怎么办」，RateLimiter 是「别把钱花太快」，三者正交，配置里分开注释。
2. **预算层：日 token 预算（用户记账、全局兜底，超限降级续跑）**
   - 记账粒度：`llm_calls` 经 `tasks.owner_id` 关联到用户；预算检查先查该用户当日 `SUM(total_tokens)`，用户配额（`workbench.llm.user-daily-token-budget`，默认关闭）未启用时只看全局预算（`workbench.llm.daily-token-budget`）。先自用只有全局闸生效，将来少数人共用时打开用户配额即可，不需要改代码。
   - **超预算降级续跑（决策 #3）**：超过预算时不再抛 `BudgetExhausted` 让任务 FAILED，而是把该次调用切换到廉价档模型（复用 `fallback-model` 降级链，新增一个 `workbench.llm.budget-fallback-model` 配置，优先级高于普通 fallback）。质量有损但任务当日可用；调用照常记账并打上 `budget_fallback` 标记，方便事后统计「预算外降级发生了多少次」。
   - 廉价档也不可用（连续失败）才退回非瞬时 FAILED，失败原因对用户可见。
3. **拒绝而非阻塞**：RateLimiter 配 `timeout-duration: 0` 快速失败。消费并发=1，阻塞 acquire 会卡死整条流水线；快失败后由降级链接手，与现有死信语义一致。
4. **可观测**：限流拒绝次数（Counter）、当日已用 token / 预算（Gauge）进 Prometheus，Grafana 面板加一格。

### 验收

- 脚本连续提交多个长视频：触发限流时行为正确（快速失败 → 降级链接手），消息进死信而非无限重试。
- 超预算场景：任务最终 COMPLETED 且结果由 `budget_fallback` 模型产出，`llm_calls` 中降级调用可按标记统计；廉价档不可用时任务 FAILED 且原因正确。
- 关闭配置开关后行为与现状完全一致（回滚路径）。
- 验收数据记入 `docs/项目数据记录模板.md`。

### 风险

- 预算检查与调用之间有竞态（并发块同时通过检查）→ 多算的部分由调用后的 usage 入账兜底，误差一轮分块内可接受，不做分布式锁。

> **实施状态（2026-10-07）**：P0 已完成。`V7__add_llm_calls_budget_fallback.sql`、`LlmBudgetGuard`、
> `LlmClient` 预算检查与降级续跑、`DownstreamResilience` 速率限制（仅 LLM，配置
> `resilience4j.ratelimiter.instances.llm`）、新增指标 `workbench.llm.rate_limit_rejections` /
> `llm.budget_fallbacks` / `llm.budget_used_today` / `llm.budget_limit`。
> 预算检查位于容错外壳之前，预算失败不污染熔断器计数。全量 155 项测试通过（MySQL 集成测试按环境自动跳过），
> 新增 `LlmClientBudgetTest` 5 项与限流拒绝用例。

## P1：视觉分支（关键帧 + OCR）

### 现状

- `TaskStage = IMPORT → AUDIO_EXTRACTION → TRANSCRIPTION → SUMMARY → COMPLETED`，只有音频单分支。
- `TaskService` 内嵌 FFmpeg 调用（`:358` 抽音频、`:512` 调 Whisper）。画面信息（板书、PPT、字幕）目前完全丢失。
- 反幻觉闸门：`ResultValidator` 的 `quote` 逐字比对 + 章节时间轴校验——**这是本项目最硬的资产，改造不能绕开它**。

### 方案

1. **新阶段 `VISUAL_EXTRACTION`**（插在 AUDIO_EXTRACTION 之后、TRANSCRIPTION 之前；`TaskStage` 加枚举值 + V7 迁移允许历史任务缺该阶段记录，恢复逻辑按「阶段缺失即跳过」处理，不强制回填）。
   - FFmpeg 场景检测抽关键帧：`select='gt(scene,0.3)'` + `fps=1/30` 保底采样防静态板书漏检，单任务上限 200 帧，存 `storage/{taskId}/frames/`。
2. **感知哈希去重**：相邻帧 pHash（JImageHash，纯 Java）汉明距离 < 10 视为重复，丢帧。
3. **OCR 引擎抽象成接口 `OcrEngine`**，先实现 **Tesseract 5.4**（`chi_sim` + `eng` 语言包，Docker 镜像加一行；决策 #4）。中文识别准确率在验收中实测基准：板书关键词命中率不达标时切换 PaddleOCR 容器实现，只换实现不动调用方。
4. **并行不抢资源**：OCR 是 CPU 密集，Whisper 是 GPU 密集。OCR 用独立有界线程池与 `runWhisper` 并行执行（抄 DOVideo 的双分支并行 + 单路失败保留另一路的降级思路）。OCR 整路失败 → 记 WARN，任务继续，产物里标注「无画面文本」。
5. **数据模型**：V8 迁移加 `video_frames(id, task_id, ts_ms, ocr_text, phash, path)`，`(task_id, ts_ms)` 唯一。（V7 已被 P0 的 `llm_calls.budget_fallback` 使用）
6. **融合进 SUMMARY，不碰校验**：`partitionTranscript` 分块时把时间重叠的 OCR 文本附在对应块尾（标注「画面文字」）；提示词升 v2（沿用现有 prompt 版本化机制）。**章节 `sourceSegmentId` 仍只允许指向转写片段，`quote` 闸门不扩到 OCR 文本**——OCR 有识别错误，不能当引文来源。
7. **前端（本轮交付，决策 #5）**：任务详情页加帧缩略图条，点击缩略图跳转播放进度到对应时间戳；OCR 文本随片段展示；SSE 推送 `VISUAL_EXTRACTION` 新阶段进度。

### 验收

- 中文课程视频样本：OCR 能命中板书关键词，人工对比新旧章节命中率，**命中率基准数据记入验收记录**（Tesseract 5.4 的换引擎决策依据）。
- 阶段耗时 p95 增量 < 30s（200 帧上限内）。
- 注入 OCR 失败（引擎不可达）：主链路仍 COMPLETED，指标里 OCR 失败可观测。
- 前端交互：帧缩略图条渲染正确，点击跳转播放时间戳准确（±1s），SSE 阶段推送可见。

### 风险

- 帧数爆炸 → 上限 + 采样兜底；磁盘占用 → 帧图随任务清理策略一起删。

> **实施状态（2026-10-07）**：P1 后端与前端已完成。`V8__add_video_frames.sql`、
> `TaskStage.VISUAL_EXTRACTION`（进度 25%）、`VisualExtractionService`（场景检测 + fps 保底两趟抽帧、
> showinfo 解析时间戳、手写 DCT pHash 相邻去重、超上限均匀抽样且首帧末帧保留）、
> `OcrEngine` 接口 + `TesseractOcrEngine`、OCR 单线程池与 Whisper 并行、抽帧/OCR 失败均降级为
> 「无画面文本」不阻断主链路、取消/删除联动终止抽帧进程并清理帧图。
> 摘要提示词升 v2（新增 `{{visualText}}` 占位符，无帧文本传空串），OCR 文本按时间归并进分块；
> `quote` 闸门与 `sourceSegmentId` 校验不扩到画面文字。新增 API：`GET /{id}/frames`、
> `GET /{id}/frames/{tsMs}/image`；前端任务详情页新增可横向滚动的关键帧条（悬停看 OCR、点击跳转播放）。
> 全量 167 项测试通过（新增 PerceptualHashTest、VisualFrameDedupTest、VisualFusionTest、FrameRepositoryTest）。
> **待验收**：中文样本的 OCR 命中率基准与阶段耗时 p95 需在装有 ffmpeg/tesseract 的本机跑真实视频后补录。
> 注意：容器内 tesseract 实际为 **4.1.1**（Ubuntu 22.04 apt 源最新版，非决策 #4 预期的 5.4），
> 中文命中率会更吃亏——若基准不达标，优先评估直接换 PaddleOCR 容器（接口抽象已就位），
> 而不是为 5.x 做源码编译。
>
> **线上事故与修复（2026-10-07）**：首个真实视频（AV1 编码发布会录像）抽帧失败——
> `fps=1/30` 滤镜在该输入上输出帧的**内容与标注时间戳错位**（首帧取到 ~15s 处画面却标成 0，
> 尾部还丢 4 个网格点），错位帧与场景通道的真第 0 帧 pHash 距离超阈值，两行同 ts 落库撞
> `uk_video_frames_task_ts` 唯一键，又被误分类为瞬时故障 `database_unavailable` 重试 4 次进死信。
> 两处修复：① fallback 采样弃用 fps 滤镜，改为 ffprobe 探时长 + 逐点 `-ss` seek 抽帧
> （时间戳由构造决定，不依赖滤镜 pts 语义；单点失败跳过不放弃整趟）；② `dedupeAndCap` 增加
> 「时间戳相同只保留一帧」硬约束（稳定排序保证场景通道优先）；③ `TaskQueueConsumer` 把
> `DataIntegrityViolationException` 从瞬时故障中分出：确定性冲突不重试，标 FAILED 进死信。
> 全量 169 项测试通过；修复后同一视频重跑成功：18 帧、时间戳全唯一、18/18 帧 OCR 有文本。

## P2：向量召回（先追问，后检索）

### 为什么排最后（诚实论证）

固定流水线的**全片摘要需要全部内容参与**，向量召回帮不上忙——这是和 DOVideo-AI 的本质区别：它的检索是为「用户输入分析目标 + 多轮追问」服务的。没有查询动作，检索系统就是没有用户的空转。所以 P2 拆两步：

### P2a：追问交互（无向量，1–2 天，**本轮范围内**）

- 任务 COMPLETED 后开放提问框；后端新接口 `POST /tasks/{id}/questions`。
- 转写全文字符数 ≤ `max-input-chars` 的视频：全文直接进上下文问答（复用 JSON Schema 校验基建，新 schema `answer.json`，要求答案必须引用 `sourceSegmentId`，**`quote` 闸门照常生效**）。
- 超长视频暂时提示「暂不支持，长视频问答在规划中」——先让小视频闭环。
- 新表 `task_questions(id, task_id, question, answer, created_at)`。

### P2b：长视频向量召回（4–6 天，**暂缓**：前置 = P2a 上线且确有长视频追问需求，决策 #6）

- **窗口摘要**：按 5 分钟窗口用新提示词 `segment-summary.v1` 生成摘要 + 关键词（离线、随 SUMMARY 阶段顺带产出）。
- **Embedding**：优先调硅基流动 BGE-M3 API（不自建）；`workbench.embedding.*` 配置段。
- **向量库**：Qdrant 单容器加进 `compose.yaml`，与现有编排方式一致；MySQL 仍是业务真源，Qdrant 只存 `(window_id, embedding)` + `task_id` payload 过滤。
- **检索**：关键词 LIKE 与 Qdrant topK 取并集 → 召回窗口 → 拉原始片段进问答上下文。
- **优雅降级**：Qdrant 或 Embedding 服务不可用时自动退回 P2a 行为（超长视频则明确报错），不阻断追问主链路。

### 验收

- 1 小时视频追问 p95 < 15s，成本 < 全量喂入的 30%。
- 降级注入：停 Qdrant，追问仍可用（全文模式或明确报错），不 500。

## 执行顺序（按决策 #6 确定的本轮范围）

```
P0 限流护栏（1–2 天）── 独立，最先做；超预算走降级续跑
P1 视觉分支（4–6 天，含前端）── 独立，价值最大
P2a 追问·全文模式（1–2 天）── 本轮收尾
P2b 向量召回（4–6 天）── 暂缓，等真实长视频追问需求出现再动工
```

本轮合计约 7–9 天。P0 与 P1 无依赖可并行；P2b 是唯一需要新中间件的改动，放本轮之外是为了让它上线的那天就有用户。
