# 改造方案与落地优先级

对标 [DOVideo-AI](https://github.com/Xiaoc7r/DOVideo-AI) 后确定的三 个改造方向，按「护栏 → 价值 → 架构」排序。
每个方向给出：现状锚点（代码位置）、方案、数据模型、验收标准、风险与回滚。

## 优先级总览

| 优先级 | 方向                        | 理由                                                                             | 预估工作量             |
| ------ | --------------------------- | -------------------------------------------------------------------------------- | ---------------------- |
| P0     | LLM 成本护栏（限流 + 预算） | 改动最小、堵住唯一的成本敞口；基建（Resilience4j、llm_calls 表）已就位           | 1–2 天                 |
| P1     | 视觉分支（关键帧 + OCR）    | 对章节质量提升最大；只加分支不动既有校验链路                                     | 3–5 天                 |
| P2     | 向量召回                    | **有前置条件**：当前产品没有「查询」动作，向量检索没有服务对象；必须先加追问交互 | P2a 1–2 天，P2b 4–6 天 |

排序原则：P0 是花钱的保险丝，先装；P1 是用户可感知的价值；P2 是架构升级，但不解决「谁在检索」之前不做。

## P0：LLM 成本护栏

### 现状

- `LlmClient.summarize`（`LlmClient.java:88-102`）按 `maxInputChars`（默认 60000，`application.yml:108`）分块，**每块一次 LLM 调用，循环无总量上限**。一个 10 小时视频 ≈ 60+ 次调用，没有任何闸门。
- 已有：`bulkhead.llm`（并发 4，`application.yml:68`）+ 熔断器——它们管「同时多少个」，不管「一共多少个」「多快」。
- `llm_calls` 表（V4 迁移）+ `LlmCostService` 已按 prompt 版本记录 token 与金额，**记账有了，限流没有**。
- 消费并发固定为 1（`TaskQueueConsumer.java:24`），所以限流对象是「单个任务内部的多块调用」，不是多任务并发。

### 方案

1. **速率层：Resilience4j RateLimiter（令牌桶）包住 `LlmClient.requestJson`**
   - 按每分钟请求数限流：`workbench.llm.rate-limit-rpm`（默认 30）。
   - 熔断/隔板是「下游坏了怎么办」，RateLimiter 是「别把钱花太快」，三者正交，配置里分开注释。
2. **预算层：日 token 预算**
   - 每次调用前查 `llm_calls` 当天 `SUM(total_tokens)`；超过 `workbench.llm.daily-token-budget` 时抛新的 `BudgetExhausted`（非瞬时故障），任务 FAILED，失败原因对用户可见「今日 AI 预算已用完」。
   - 不做「等明天再跑」的排队：当前没有调度器，排队就是僵尸任务。
3. **拒绝而非阻塞**：RateLimiter 配 `timeout-duration: 0` 快速失败。消费并发=1，阻塞 acquire 会卡死整条流水线；快失败 + 任务可见失败 + 用户手动重试，与现有死信语义一致。
4. **可观测**：限流拒绝次数（Counter）、当日已用 token / 预算（Gauge）进 Prometheus，Grafana 面板加一格。

### 验收

- 脚本连续提交多个长视频：`llm_calls` 当日总量不超过预算；触发限流时任务失败原因正确、消息进死信而非无限重试。
- 关闭配置开关后行为与现状完全一致（回滚路径）。
- 验收数据记入 `docs/项目数据记录模板.md`。

### 风险

- 预算检查与调用之间有竞态（并发块同时通过检查）→ 多算的部分由调用后的 usage 入账兜底，误差一轮分块内可接受，不做分布式锁。

## P1：视觉分支（关键帧 + OCR）

### 现状

- `TaskStage = IMPORT → AUDIO_EXTRACTION → TRANSCRIPTION → SUMMARY → COMPLETED`，只有音频单分支。
- `TaskService` 内嵌 FFmpeg 调用（`:358` 抽音频、`:512` 调 Whisper）。画面信息（板书、PPT、字幕）目前完全丢失。
- 反幻觉闸门：`ResultValidator` 的 `quote` 逐字比对 + 章节时间轴校验——**这是本项目最硬的资产，改造不能绕开它**。

### 方案

1. **新阶段 `VISUAL_EXTRACTION`**（插在 AUDIO_EXTRACTION 之后、TRANSCRIPTION 之前；`TaskStage` 加枚举值 + V7 迁移允许历史任务缺该阶段记录，恢复逻辑按「阶段缺失即跳过」处理，不强制回填）。
   - FFmpeg 场景检测抽关键帧：`select='gt(scene,0.3)'` + `fps=1/30` 保底采样防静态板书漏检，单任务上限 200 帧，存 `storage/{taskId}/frames/`。
2. **感知哈希去重**：相邻帧 pHash（JImageHash，纯 Java）汉明距离 < 10 视为重复，丢帧。
3. **OCR 引擎抽象成接口 `OcrEngine`**，先实现 Tesseract（`chi_sim+eng`，Docker 镜像加一行）。Tesseract 中文准确率不够时换 PaddleOCR 容器，只换实现不动调用方。
4. **并行不抢资源**：OCR 是 CPU 密集，Whisper 是 GPU 密集。OCR 用独立有界线程池与 `runWhisper` 并行执行（抄 DOVideo 的双分支并行 + 单路失败保留另一路的降级思路）。OCR 整路失败 → 记 WARN，任务继续，产物里标注「无画面文本」。
5. **数据模型**：V7 迁移加 `video_frames(id, task_id, ts_ms, ocr_text, phash, path)`，`(task_id, ts_ms)` 唯一。
6. **融合进 SUMMARY，不碰校验**：`partitionTranscript` 分块时把时间重叠的 OCR 文本附在对应块尾（标注「画面文字」）；提示词升 v2（沿用现有 prompt 版本化机制）。**章节 `sourceSegmentId` 仍只允许指向转写片段，`quote` 闸门不扩到 OCR 文本**——OCR 有识别错误，不能当引文来源。
7. **前端**：任务详情加帧缩略图条（点击跳转播放），SSE 推新阶段。

### 验收

- 中文课程视频样本：OCR 能命中板书关键词，人工对比新旧章节命中率。
- 阶段耗时 p95 增量 < 30s（200 帧上限内）。
- 注入 OCR 失败（引擎不可达）：主链路仍 COMPLETED，指标里 OCR 失败可观测。

### 风险

- 帧数爆炸 → 上限 + 采样兜底；磁盘占用 → 帧图随任务清理策略一起删。

## P2：向量召回（先追问，后检索）

### 为什么排最后（诚实论证）

固定流水线的**全片摘要需要全部内容参与**，向量召回帮不上忙——这是和 DOVideo-AI 的本质区别：它的检索是为「用户输入分析目标 + 多轮追问」服务的。没有查询动作，检索系统就是没有用户的空转。所以 P2 拆两步：

### P2a：追问交互（无向量，1–2 天）

- 任务 COMPLETED 后开放提问框；后端新接口 `POST /tasks/{id}/questions`。
- 转写全文字符数 ≤ `max-input-chars` 的视频：全文直接进上下文问答（复用 JSON Schema 校验基建，新 schema `answer.json`，要求答案必须引用 `sourceSegmentId`，**`quote` 闸门照常生效**）。
- 超长视频暂时提示「暂不支持，长视频问答在规划中」——先让小视频闭环。
- 新表 `task_questions(id, task_id, question, answer, created_at)`。

### P2b：长视频向量召回（4–6 天，前置 = P2a 上线且确有长视频需求）

- **窗口摘要**：按 5 分钟窗口用新提示词 `segment-summary.v1` 生成摘要 + 关键词（离线、随 SUMMARY 阶段顺带产出）。
- **Embedding**：优先调硅基流动 BGE-M3 API（不自建）；`workbench.embedding.*` 配置段。
- **向量库**：Qdrant 单容器加进 `compose.yaml`，与现有编排方式一致；MySQL 仍是业务真源，Qdrant 只存 `(window_id, embedding)` + `task_id` payload 过滤。
- **检索**：关键词 LIKE 与 Qdrant topK 取并集 → 召回窗口 → 拉原始片段进问答上下文。
- **优雅降级**：Qdrant 或 Embedding 服务不可用时自动退回 P2a 行为（超长视频则明确报错），不阻断追问主链路。

### 验收

- 1 小时视频追问 p95 < 15s，成本 < 全量喂入的 30%。
- 降级注入：停 Qdrant，追问仍可用（全文模式或明确报错），不 500。

## 建议执行顺序

```
P0 限流护栏（1–2 天）── 独立，随时可做，建议最先
P1 视觉分支（3–5 天）── 独立，价值最大
P2a 追问（1–2 天）── 独立
P2b 向量召回（4–6 天）── 依赖 P2a，且等真实长视频需求出现再动工
```

P0 与 P1 无依赖可并行；P2b 是唯一需要新中间件的改动，放最后是为了让它上线的那天就有用户。
