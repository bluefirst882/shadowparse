## 2026-09-27 章节引文闸门（反幻觉）与跨块二次合并

- 契约变化：章节输出新增 `quote` 字段，语义为**该章节所引用片段（`sourceSegmentId..sourceEndSegmentId`）的转写原文原句**。
  提示词明确要求「逐字摘自所引用片段、不得改写/翻译/概括」，服务端会核验。
- 校验新增：`quote` 非空，且归一化后（去掉空白与中英文标点）必须连续出现在所引用片段的转写文本中；不符则按幻觉处理，
  抛出可读异常（含章节序号、标题与引文）并触发重试。归一化只容忍标点/空白差异，不做前缀、关键字或编辑距离等宽松匹配。
- 重试增强：`LlmClient.summarize(transcript, maxInputChars, previousError)` 增加可空的「上次失败原因」参数；
  `TaskService.generateContent` 把上一次的校验失败原因回灌到提示词末尾「上次输出未通过校验：<原因>，请修正后重新返回完整 JSON」。
  理由：同一个提示词重试大概率仍是同样的幻觉，带上失败原因才有意义。
- 新增指标：`workbench.llm.validation_failures`（Prometheus `workbench_llm_validation_failures_total`，标签 `reason=quote_mismatch`
  / `quote_missing` / `invalid_chapter_*`），每次校验拦下打点，使「闸门到底拦住了几次」可被观测。
- 去掉静默截断：删除 `keyPoints` 的 `distinct().limit(12)`；保留 12 作为宽松告警阈值（继承旧截断值），超出只打日志告警并给出实际条数，绝不丢弃。

## 2026-09-27 JSON Schema 结构约束与模型降级链

- 契约变化：摘要、跨块合并、翻译三类响应各自绑定一份 JSON Schema，schema 定义在 `LlmJsonSchema`（唯一来源），
  同一份原文既写入提示词约束模型，也用于服务端本地逐字段校验。校验不再只判断顶层字段是否为 `null`，而是按 JSON 路径
  报出缺失的必填字段与类型错误；空内容、非法 JSON、结构不符三类分别计入 `workbench_llm_output_failures_total`。
- 供应商能力实测（DeepSeek 官方 API，结果决定实现方式而不是反过来）：`response_format={"type":"json_schema",...}` 返回
  `400 This response_format type is unavailable now`；强制 function calling（`tool_choice`）返回
  `400 Thinking mode does not support this tool_choice`；只有 `response_format={"type":"json_object"}` 返回 `200`。
  因此最终采用 `json_object` + 提示词内 schema 原文 + 本地机械校验，未使用供应商侧结构化输出。
- 降级契约：新增 `LLM_FALLBACK_MODEL`（默认 `deepseek-v4-pro`），主模型在超时、HTTP 报错或输出结构不可用时升级重试一次，
  降级按原因打点 `workbench_llm_fallbacks_total` 并写 WARN 日志；留空即关闭降级。主模型失败与备用模型成功**分别记账**，
  失败不会被降级掩盖。
- 后端 `mvnw verify` 通过：`Tests run: 87, Failures: 0, Errors: 0, Skipped: 3`（MySQL 集成测试未配置 `MYSQL_TEST_URL` 时跳过），

  （主模型 400 / 备用模型 200），断言降级计数标签 `reason=http_400`、输出结构失败的三种原因，以及备用模型留空或同名时**不**回退。

## 2026-09-27 任务队列外置到 RabbitMQ（P2-1）

- 验收标准（计划原文）：**重复投递只被消费一次；重启后任务不丢**。两条均在容器环境实测通过。
- 变更：删掉进程内的单线程 `ThreadPoolExecutor` + `ArrayBlockingQueue`（原来重启即丢），
  改为「先落库 `QUEUED` 再投递消息」，队列外置到 RabbitMQ 4（持久化队列 + 持久化消息 + 手动 ack）。
  `TaskService` 只依赖 `TaskQueue` 接口，`RabbitTaskQueue` 提供实现，`TaskQueueConfig` 声明
  `workbench.tasks`（DLX → `workbench.tasks.dlx`）、`workbench.tasks.retry`、`workbench.tasks.dead` 三个持久化队列。
- **重复只消费一次**：把一条已完成任务改回 `QUEUED/IMPORT`，在 backend 停机期间用管理 API 向 `workbench.tasks`
  直投 **3 条内容相同**的消息；启动后端后日志出现 **3 次**「任务已被领取或已结束，跳过重复投递」，
  连同启动恢复自己重投的 1 条共 4 条消息，任务只被真正处理 1 次并最终 `COMPLETED`。
  幂等的裁决点是数据库条件更新 `claimForProcessing`（`where id=? and status='QUEUED' and cancelled=false`），
  不依赖队列的去重能力——因此「broker 重投」「用户连点重试」「多实例并发消费」都只会执行一次。
- **重启后任务不丢**：上述消息是在进程停止期间投递的，broker 持久化保存、重启后被正常消费；
  崩溃时那条未确认的消息也会由 broker 重新投递。启动顺序被明确约束为
  `TaskRecovery` 先 `recoverAfterRestart()` 把残留 `PROCESSING` 改回 `QUEUED` 并重投，
  **再** `consumer.start()`；顺序反了会让重投的消息因任务仍是 `PROCESSING` 而被白白确认、任务永久卡住。
- 队列不可用不假装成功：投递抛异常时任务保持 `QUEUED` 并带「消息队列暂不可用」提示返回
  （导入接口返回 503、任务记录仍在），异步拒收只计 `workbench.queue.publish_failures` 与 ERROR 日志，
  不做「静默停在 QUEUED」。
- 正常链路回归：20 秒样本上传后 `QUEUED` → `TRANSCRIPTION(45%)` → `SUMMARY(85%)` → `COMPLETED`（约 27 秒）；
  `workbench_queue_depth 0.0` 读自 broker 真实积压量，`workbench_queue_wait_seconds_count 1` 记录到一次等待时长。
- 配置陷阱已处理：RabbitMQ 默认 `consumer_timeout` 为 30 分钟，短于本项目 `WORKBENCH_PROCESS_TIMEOUT_MINUTES=180`，
  长视频会在处理中被强制关 channel；容器用 `RABBITMQ_SERVER_ADDITIONAL_ERL_ARGS` 放宽到 24 小时，
  实测 `application:get_env(rabbit, consumer_timeout)` 返回 `{ok,86400000}`。
- 后端 `mvnw verify` 通过：`Tests run: 108, Failures: 0, Errors: 0, Skipped: 3`，Spotless 通过。
- 局限（如实记录）：重复投递是用管理 API 人为直投制造的，不是网络抖动自然产生的重复；
  重试与死信队列拓扑已声明，但「重试 → 超限 → 死信」的退避路径属于 P2-2，本次未跑通；
  发布确认失败仅在单元测试中验证计数，尚无真实拒收流量；多实例并发消费（`FOR UPDATE SKIP LOCKED`）属于 P2-4，尚未验收。

## 2026-09-27 LLM 与 Whisper 的容错治理（P2-3）

- 验收标准（计划原文）：**下游挂掉时接口快速失败而非线程堆积，熔断状态可观测**。两条均在容器环境实测通过。
- 变更：引入 `resilience4j-spring-boot3` 2.3.0，新增 `DownstreamResilience` 统一给 LLM 与 Whisper 两侧加
  **并发隔板（外）+ 熔断器（内）**。顺序不能反：隔板在最外层，被本地拒绝的调用不会记成下游故障，
  否则并发满时会把熔断器误推向打开。LLM 的 HTTP 超时改由 `workbench.llm.timeout-seconds`（默认 90 s）与
  `translate-timeout-seconds`（默认 180 s）配置、由 JDK `HttpRequest.timeout` 强制。
- 刻意**不叠加** Resilience4j 的 Retry 与 TimeLimiter，理由写进了 `DownstreamResilience` 的注释：
  重试已经有三处归属（模型降级链 flash→pro、任务内 3 次重新生成、队列指数退避），再叠一层会叠加放大；
  TimeLimiter 只能让调用方提前返回、藏不住仍在跑的请求，超时交给 HTTP 客户端强制更诚实。
  也**不注册熔断器健康指示器**：熔断打开代表下游不健康，不代表本进程该被重启，算进 `/actuator/health`
  会导致容器健康检查失败被无谓重建。
- 配置（`application.yml` 的 `resilience4j` 段）：`llm` 窗口 10 / 最小样本 5 / 失败率 50% / 打开后等 30 s /
  半开放行 3；`whisper` 窗口 6 / 最小样本 3 / 失败率 50% / 打开后等 60 s / 半开放行 2。
  并发隔板 `llm` 4、`whisper` 1（可用 `WORKBENCH_LLM_MAX_CONCURRENT` / `WORKBENCH_WHISPER_MAX_CONCURRENT` 调），
  `max-wait-duration: 0` 即**不排队、直接拒绝**——这正是「快速失败而非线程堆积」的实现方式。

  `workbench_llm_requests_total{outcome="failure"}` 是 1:2 的关系，两者不能混着读；
  首次实测把 `minimum-number-of-calls` 设成 10 就因此没能触发熔断，已改为 5 并写注释说明。
- **Whisper 侧熔断实测**（故障注入：把容器 `WHISPER_SERVICE_URL` 覆盖为黑洞地址 `http://192.0.2.1:8090`，

## 2026-09-27 多实例任务认领与租约（P2-4）

- 验收标准（计划原文）：**起两个实例并发消费同一队列，无重复执行**。已在容器环境用两个真实实例实测通过。
- 变更：把「状态即锁」升级为**租约持有**。`claimForProcessing` 仍用条件更新
  （`update ... set status='PROCESSING' where id=? and status='QUEUED' and cancelled=false`）做幂等唯一裁决点，
  但额外写入 `locked_by`（实例 id）与 `lease_expires_at`（迁移 V5 加列 + `idx_tasks_lease`）。
  新增 `TaskLease`：持有者按 `WORKBENCH_LEASE_HEARTBEAT_MILLIS` 续**自己**在跑的任务（内存 `Set<String> held`，
  只续真正在跑的，避免把被放弃的行续到永不过期），并按 `WORKBENCH_LEASE_SWEEP_MILLIS` 巡检
  `status='PROCESSING' and lease_expires_at < now` 的行——含迁移前遗留的 `lease_expires_at is null` 行，
  按「已过期」处理，升级过程中被中断的任务不会卡住。
- 为什么必须改：旧方案在**多实例**下有两个漏洞。一是启动恢复把**所有**残留 `PROCESSING` 改回 `QUEUED`，
  第二个实例一启动就会把第一个实例正在跑的任务重投一遍；二是没有任何字段能区分「别的实例在跑」与「持有者已经死了」，
  只能二选一（要么抢别人的活，要么让崩溃的任务永远卡在 `PROCESSING`）。
- 三种恢复路径现在各自有归属：优雅停机（`@PreDestroy`）调 `releaseClaimsOwnedBy(instanceId)` **立刻**交还；
  被 `SIGKILL` 崩溃靠租约过期 + 巡检回收重投；重试投递（`attempt>1`）先 `releaseIfAbandoned`，
  仅当 `locked_by=自己` 或租约已过期时就地放回，否则直接 return，绝不抢别的实例的活。

## 2026-09-29 Whisper 容器化与自愈（P3-1）

- 背景：P2-4 的崩溃接管实测里，两个后端实例同时向**宿主机 GPU 上的同一个 Whisper** 发转写，Whisper 返回
  `500 CUDA out of memory`，任务退避用尽后进死信；而且宿主机 worker 是手工起的进程，「悄悄死掉」只会让后端报
  `ConnectException`，没有任何自愈手段。本次把 worker 收进容器托管，并顺带在 worker 内把转写串行化。
- 交付：新增 `workers/Dockerfile`（python:3.12-slim + ffmpeg + CPU 版 `torch==2.5.1+cpu` +
  `openai-whisper==20250625`，用 `--no-deps` 跳过 Linux 上会被带进来的 triton）；
  `compose.yaml` 新增 `whisper` 服务（healthcheck 打 `/health`、`restart: unless-stopped`、
  模型目录 `WHISPER_MODELS_DIR` 挂到 `/models`、容器 8090 映射到宿主机）；后端 `WHISPER_SERVICE_URL` 默认改为
  `http://whisper:8090` 并加 `depends_on: whisper: service_healthy`；
  `whisper_worker.py` 改为**启动时加载模型**（按 `(模型名, 设备)` 缓存）并给 `/transcribe` 加锁串行执行。
- 实测（2026-09-29，本机 Docker Desktop，CPU 推理）：
  - 镜像 `toni-2-whisper:latest` 2.22GB，构建日志末行为 `torch 2.5.1+cpu cuda False`。
  - 容器日志顺序是先 `Whisper model ready: turbo on cpu`、后
    `Whisper service listening on ('0.0.0.0', 8090); device=cpu`；权重来自挂载
    `E:\program\project\toni-2\models\whisper -> /models`（`large-v3-turbo.pt` 1617941637 字节，未触发下载）。

## 2026-09-29 压测与容量说明（P3-2）

目标：给出「这套系统在单机上到底能扛多少」的实测数字，并找到第一个瓶颈，而不是宣称一个容量。

脚本（`ops/k6/`，`fixtures/` 与 `results/` 已在 `.gitignore` 中）：

- `lib.js`：`login()` 拿 JWT、`taskIds()` 取一批真实任务 id、`report()` 自拼 Summary（k6 的

- `query.js`：`ramping-arrival-rate` 打列表 / 详情 / 明细 三个读接口，按 7:2:1 混合，分别打

- `upload.js`：`constant-arrival-rate` 以恒定到达率 POST multipart 上传 48,701 字节的 4 秒真实视频片段。
- `sample-queue.ps1`：每 5 秒采样一次队列深度与该批次任务的状态分布，写 `ops/k6/results/queue.csv`。

### 读接口容量

两轮阶梯加压，每档 30s，共 120s；请求总数 43000+，`http_req_failed` 与 `dropped_iterations` 均为 0。

| 场景           | 到达率（次/秒） | 请求数 | P95 列表 | P95 详情 | P95 明细 | 失败率 |
| -------------- | --------------- | ------ | -------- | -------- | -------- | ------ |
| 第一轮 20→120  | 20/40/80/120    | 19440  | 1.91ms   | 1.76ms   | 2.75ms   | 0      |
| 第二轮 100→400 | 100/200/300/400 | 23880  | 2.14ms   | 1.93ms   | 3.11ms   | 0      |

即便在 400 次/秒的到达率下，P95 仍在个位毫秒级、没有失败——**读路径没有压出拐点**，因此本节**不给最大 QPS**，

### 上传路径

恒定到达率两轮：2 次/秒 × 20s 造出 40 个任务、2 次/秒 × 30s 造出 61 个任务（合计 101），

### 服务端侧对照

同一稳态（200 次/秒 × 40s，8001 个请求）下从 Prometheus 取服务端侧分位数：

| ------------------------------------- | ---------- | ---------- |
| `GET /api/tasks`（列表）              | 2.05ms     | 4.31ms     |

`management.metrics.distribution.percentiles-histogram.http.server.requests`——Micrometer 默认的
Timer 只导出 `_count/_sum/_max`，**没有 `_bucket`**，`histogram_quantile` 会静默返回空。

### 资源占用

压测期间（`docker stats` 采样）：backend 37–48% CPU / 557MiB、mysql 14–17% / 199MiB、
whisper 约 0.01%（空闲，只在跑转写时争 CPU）/ 3.37GiB；HikariCP `pending` 全程为 0。

### 瓶颈：不在接口，在处理侧

`ops/k6/results/queue.csv` 显示积压随上传线性上涨后靠处理侧慢慢掉：

| 时刻     | 队列深度 | queued | completed |
| -------- | -------- | ------ | --------- |
| 16:01:33 | 97       | 97     | 3         |
| 16:02:37 | 95       | 95     | 5         |
| 16:04:20 | 91       | 91     | 9         |

即队列深度涨到 **97**（101 个任务里 97 个在排队、1 个在处理），而排空速率约 **2 个/分钟**，与到达速率（120 个/分钟）差 60 倍以上。
根因是 Whisper 在 CPU 上对 4 秒片段也要约 10s（日志 `401/401 frames`、39–40 frames/s），叠加后端
`WORKBENCH_WHISPER_MAX_CONCURRENT=1` 的隔板。系统表现为「**接口永远很快、积压线性增长**」：
没有背压、没有拒绝策略，积压只能靠消费者慢慢消化（这条已记入 README 的「当前不支持与下一步」）。

- 局限（如实记录）：
  - **单机同机压测**：k6、backend、mysql、whisper 抢同一份 CPU 与磁盘，数字不能外推为生产容量。
  - 上传场景只压接收路径，**不是端到端 QPS**；端到端能力由 Whisper 串行处理决定（上表）。
  - 未做长时间稳定性（soak）与读写混合压测，排空曲线只覆盖约 100 秒。
  - 读接口未压出拐点，所以**不给最大 QPS**；400 次/秒只是本次验证到的下界。
  - 压测造的 101 个 `sample-4s.mp4` 任务已在测完后通过 API 清理（`deleted=101`），清理后队列深度回到 0。

## 2026-09-29 前端实时推送与分片上传（P3-3）

目标：界面不再靠定时轮询拿进度，任务状态变化由服务端主动推；大文件上传带进度，中途断了重选同一个文件能接着传。

### 做法

- **SSE 推送**（[TaskEventStream.java](file:///e:/program/project/toni-2/backend/src/main/java/ai/toni/videoworkbench/TaskEventStream.java)）：
  `TaskRepository` 每次写完任务状态都会调 `taskChanged(taskId)`。推的是**信号（只带任务号）**而不是整行数据——
  客户端收到后按自己已鉴权的接口重新取数，推送通道因此不必再复制一套归属校验与序列化，
  也不会把别的账号的任务内容带到某个连接上（通知只发给该任务的归属人）。没有任何订阅者时连归属人都不查，
  原有处理路径的开销不变。连接 30 分钟到期后关闭，由浏览器自动重连。
  `GET /api/tasks/stream` 与视频流同理用 `access_token` 查询参数带令牌（`EventSource` 不能自定义请求头）。
- **前端**（[App.vue](file:///e:/program/project/toni-2/frontend/src/App.vue)）：3 秒轮询整体删除，改为 `EventSource`
  ＋ 120ms debounce 合并刷新（一次上传会连续写好几次状态，合并后只发一次列表请求）；`onopen` 时补刷一次，
  `onerror` 时退回一次主动刷新兜底。
- **分片上传**（[ChunkedUploadService.java](file:///e:/program/project/toni-2/backend/src/main/java/ai/toni/videoworkbench/ChunkedUploadService.java)）：
  `CHUNK_SIZE = 5 MiB`；`uploadId = sha256(ownerId + "\n" + 文件名 + "\n" + 大小)` 的前 16 字节——
  **重选同一个文件必然得到同一个 id**，所以续传对客户端是无状态的（不需要它自己记住上次传到哪）。
  进度存在文件系统 `storage/uploads/<uploadId>/`：`meta.properties`（文件名/大小/归属人）、
  按偏移直接写入的 `data.part`、每片一个 `chunk-N.done` 标记（**标记最后写**，因此「有标记」等价于「该片已落盘」）。
  不额外建表，进程重启后进度还在。`complete` 校验分片齐全且文件大小等于声明值后才登记任务，登记成功才删会话目录。
- **前端分片用 XHR 而不是 fetch**：上传方向的进度事件目前只有 XHR 提供，进度条靠它驱动。

### 实测

**一、浏览器端**（`npm run verify:realtime-upload`，Playwright + 真实 Chrome，经 nginx `127.0.0.1:5174`）：

```text
登录完成，既有任务 15 行
空闲 8s 内 /api/tasks 列表请求数=0（轮询已移除，应为 0）
SSE：{"connections":1,"events":0}（连接应为 1）
  <-- 200 POST /api/tasks/uploads
  <-- 200 PUT /api/tasks/uploads/00c307.../chunks/0
  <-- 200 POST /api/tasks/uploads/00c307.../complete
[17:21:23.519] 新任务行出现（未手动刷新、未轮询）
[17:21:23.524] verify-small-...mp4 0 MB · 本地转写 45%
[17:21:39.253] verify-small-...mp4 0 MB · 生成内容 85%
[17:21:46.268] verify-small-...mp4 0 MB · 已完成 100%
阶段变化次数=3；推送事件=6；由推送触发的列表刷新=4
[17:21:47.804] 上传进度 UI：上传中 17%（进度条 aria-valuenow=17，可见）
  <-- 200 PUT .../chunks/0 / 1 / 2
[17:21:48.062] 大文件分片上传完成并出现在列表中
```

- **空闲 8 秒零列表请求**：这是「轮询真的删掉了」的直接证据（改造前每 3 秒一次，8 秒内必然 ≥2 次）。
- **阶段文字自动变化 3 次而无人刷新**，推送事件 6 次、触发的列表刷新 4 次——推送确实在驱动界面，
  刷新次数少于事件次数正是 120ms debounce 合并的效果。
- 进度条读数是**真实限速下的真实上传进度**（脚本用 CDP 把上传带宽压到 1.5 MiB/s 再采样，不是在
  Playwright 里把请求拦下来延后放行——那样浏览器不会派发上传进度事件，读出来恒为 0）。截图
  [docs/前端分片上传进度.png](file:///e:/program/project/toni-2/docs/前端分片上传进度.png)。

**二、推送延迟与账号隔离**（`npm run verify:sse`，直连 `8081`）：

```text
无令牌订阅 -> HTTP 401（应为 401）
[ready] 订阅确认，用时 8ms
本任务收到推送 6 次，其中 6 次可与同一次写入对上账：6ms, 8ms, 7ms, 9ms, 7ms, 5ms
推送延迟 min=5ms 中位=7ms max=9ms
SSE 订阅已建立：true
另一账号（sse_probe_73916095）收到的推送：["ready:ok"]（应为空）
```

- 延迟口径：收到推送后立刻回查 `GET /api/tasks/{id}`，用服务端的 `updated_at` 当作这次写入的时刻，
  差值即「状态变化 → 界面收到信号」的端到端时间。同一个上传会连续写好几次（落库、认领、阶段推进），
  若回查时任务已经又变了，这个差值就不再对应同一次写入，脚本会丢弃而不是报一个假数（本次 6 次全部对得上账）。
- 另一个账号在同一个后端上订阅，整个过程中**只收到 `ready`**，没有收到任何关于该任务的推送。
- 无令牌订阅返回 `401`（伪造令牌同样是 `401`，早前用一次性脚本测过）。

**三、分片断点续传**（curl 直打 `8081`，12,662,260 字节 / 3 片）：

```text
文件 resume-172631.mp4 大小 12662260
init uploadId=626e49f58c2a56496bc37a27f01fb8b5 chunkSize=5242880 已收分片=
PUT 0 -> 200 ; PUT 2 -> 200（跳过 1，模拟中断）
服务端已收分片=0,2
重选同一文件 -> uploadId=626e49f58c2a56496bc37a27f01fb8b5 已收分片=0,2（应一致）
PUT 补缺的 1 -> 200
complete -> task=661b9cb3... sizeBytes=12662260（应等于 12662260）
```

- 乱序补片（先 0/2 后 1）能正确落盘，最终登记的任务大小与源文件逐字节一致；
  `complete` 后会话目录被清空（`/app/storage/uploads` 计数回到 0）。

**四、浏览器端验证期间暴露并修掉的两个问题**（都是只在真实浏览器里才出现的）：

1. 分片 PUT 一直返回 `403`，响应体是 `Invalid CORS request`：`CorsConfig.allowedMethods` 里没有 `PUT`。
   浏览器对**同源**的写请求也会带 `Origin` 头，方法不在白名单里照样按跨域拒绝——而 curl 不带 `Origin`，
   所以同一端点用 curl 打一直 200，看代码也看不出问题。已补上 `PUT`，并加了回归用例
   `ApiErrorResponseTest.allowsCrossOriginChunkUploadWithPut`（断言带 `Origin` 的 PUT 返回 200 且响应带
   `Access-Control-Allow-Origin`）。
2. 进度条 `el-progress` 自身没有宽度（Element Plus 靠父容器撑开），放在按内容定宽的网格项里会塌成 0 宽：
   DOM 里有、可访问性树里 `aria-valuenow` 也在变，但**人眼看不见**。已显式给 `.uploader .el-progress` 定宽。

### 局限（如实记录）

- **推送没有心跳**。`TaskEventStream` 只在任务真的变化时才写数据，中间代理（nginx/公司网关）若按空闲超时
  断开连接，客户端要等浏览器自己发现断链才重连，期间的变化靠 `onerror` 时的一次主动刷新兜底，**不是实时**。
- **半截上传没有清理策略**。会话目录靠 `complete` 成功时删除，用户传一半就关页面会留下 `storage/uploads/<id>/`
  占着磁盘（本次调试期间就留下了 3 个），既没有 TTL 清理也没有容量配额。
- **续传是「同名同大小」级别**，不是内容校验：改了内容但文件名与大小不变的文件会被当成同一个会话继续传，
  只传缺的分片就会拼出错误内容。要严格就得让客户端上传内容哈希并纳入 `uploadId`（当前未做）。
- **进度条按分片粒度更新**：`uploadId` 由文件名与大小派生，所以「同一个文件换个目录再选一次」会被认为是续传，
  这是刻意的取舍（后端看不到目录）。
- SSE 是**单实例内存态**：`subscribers` 在进程内，多实例部署时 A 实例上的变化推不到连在 B 实例上的浏览器
  （当前部署是单实例，已在 README 的「当前不支持与下一步」中记明）。
- 浏览器端实测跑在 `127.0.0.1:5174`（nginx）与 `localhost:8081` 两类入口上；**只在这两种拓扑下验证过**，
  未验证跨域部署（前后端不同站点）下 `EventSource` 与分片 PUT 的 CORS 行为。
- 浏览器端与推送延迟的脚本都会真实创建一个任务用于触发状态变化，脚本结束时用 API 删除；
  任务本身仍会被 Whisper 真实转写一次，因此每次运行会占用一次转写算力。
